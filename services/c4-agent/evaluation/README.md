# Evaluation

## Tourism test set v1 (Layer 2)

100 tourist questions with gold answers, written against the agent's tool definitions
(`src/tools/definitions.py`, version 1.0.0). Used for evaluation only - never for training.

| Category | n (v1) | Target (final) | Correct behaviour |
|---|---|---|---|
| single_tool | 25 | 60 | one call to the right tool with the right arguments |
| multi_tool | 20 | 50 | parallel calls, or two steps (e.g. recommend_hotels -> plan_itinerary on the top hotel) |
| web_search | 15 | 40 | web_search (information no team component provides) |
| direct_answer | 12 | 30 | no tool call (greetings, thanks, answers already in the conversation) |
| decline | 12 | 30 | no tool call (out of scope or harmful requests) |
| tricky_arguments | 16 | 40 | correct budgets, guest counts, dates, nearby needs, hours |

Files:
- `testset_items.py` - the questions and gold answers, in readable form. **Edit here.**
- `build_testset.py` - validates and writes `data/tourism_testset_v1.jsonl` and `.csv`
  (`python -m evaluation.build_testset`). A test fails if the files are out of date.
- `data/tourism_testset_v1.csv` - open in Excel to review.

Build checks: every gold call is valid against the tool schemas; every hotel the user names
exists in Component 1's data; for two-step questions the second step continues with the
top hotel returned by the (mock) C2 service, and that tool result is stored with the item
so evaluation is deterministic.

Gold conventions (see the top of `testset_items.py`): listed arguments must match;
`alt(...)` accepts alternatives; `opt(v)` may be omitted; unlisted arguments are wrong unless
they are free text that cannot be judged exactly (`recommend_hotels.interests`, `top_k`
when the user gave no number, `web_search.query`).

Still to do for the final thesis: extend to 250 items, and have a second annotator label a
20% sample (Cohen's kappa >= 0.80, as in the proposal).

## Decoding-mode experiment (Steps 7-8)

Notebook: `notebooks/02_evaluate_decoding.ipynb` (generated by `python -m evaluation.build_eval_notebook`).

| File | Purpose |
|---|---|
| `decoding.py` | the 4 modes: prompts, XGrammar structural tag ("every `<tool_call>` must be a valid call"), greedy generation |
| `scoring.py` | strict scoring (tourism gold rules, BFCL-style AST check), validity, wrong-but-valid, McNemar + Holm, bootstrap CIs |
| `run_eval.py` | runs model x mode x item, resumable, writes `predictions.jsonl`, `results.json`, `results_table.csv` |
| `build_bfcl_subset.py` | seeded 100 + 100 + 100 sample of BFCL v4 simple / multiple / irrelevance -> `data/bfcl_v4_subset.jsonl` |

Hypotheses reported automatically (proposal): H1 constraint tax > 0 (free vs grammar accuracy, McNemar),
H2 grammar raises validity without raising accuracy, H3 reason_grammar is the best mode, H4 (tax shrinks
with size) by comparing the 0.5B and 1.5B result files.

Note: the BFCL check is a re-implementation of BFCL's AST matching (string normalisation, optional
parameters, no unexpected parameters). Before the final thesis it should be cross-checked against the
official BFCL checker (proposal: pipeline validated against xLAM-2-1B within +/-3 points).
